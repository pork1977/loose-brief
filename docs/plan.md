# Loose Brief: build plan

Working title in the original spec was BRANDCRAFT. Renamed on 2026-09-13, see "Names" below.

Loose Brief is an AI studio that takes a loose business brief and turns it into a brand identity and a working website. The brand decisions are stored as design tokens, so a change in one place carries through the brand system, the website and the exports.

Main journey:

Brief > brand strategy > three directions > selected identity > design tokens > website > Creative Director refinements > export

The demo brand is **Ebbfield**, a fictional AI coastal conservation startup (was TIDELINE in the spec).

## Decisions taken

1. **Names**: Loose Brief and Ebbfield.
2. **AI mode: demo data plus a capped server-side model.** The Ebbfield journey is built in and never calls a model, so the portfolio demo can't be broken by an outage or a rate limit. A visitor who writes their own brief can run it through Claude on the server, rate limited, with its own Anthropic key and a spend limit set in the console (the same setup as the PaulOS Ask app).
3. **Labelling**: built-in demo output is labelled as a demo. Anything that came from the model is labelled as generated by Claude. Nothing simulated is presented as a live AI result.

## Technical approach

### Stack

- Next.js 16, React 19, TypeScript, plain CSS.
- `zod` for every schema: the brief, a direction, the token set, a website section and a refinement change. The built-in demo data is validated against the same schemas the model has to satisfy, so the demo and live mode can't drift apart.
- `@anthropic-ai/sdk` on the server only, for live mode.
- No database. Project state lives in the browser.

### Why no Tailwind in the app itself

The whole product is about CSS custom properties that change at runtime. Generated brands can't be expressed as Tailwind classes compiled at build time, so plain CSS variables are the more honest fit. A Tailwind theme is still one of the exports.

### Two separate token layers

- **App tokens**: Loose Brief's own look (the studio chrome, panels, buttons). These never change when a user edits a brand.
- **Brand tokens**: the generated identity. Applied as CSS variables on a wrapper element around the website preview and the component examples, and nowhere else.

Keeping them apart stops a user's neon lime brand from recolouring the editor they're using to make it.

### Token pipeline

```text
Direction (validated)
  > BrandTokens  (typed, semantic names: color.brand.primary, radius.card ...)
  > compileTokens()  > { "--color-brand-primary": "#083B66", ... }
  > style attribute on the brand wrapper
```

Every exporter reads the same `BrandTokens` object: CSS variables, JSON (W3C Design Tokens format), Tailwind v4 `@theme`, `DESIGN.md` and the brand guidelines HTML. A token inspector records which website elements use each token, so a change can show what it affects.

Colour variables are registered with CSS `@property`, which lets the browser animate between palettes rather than snap.

### Website preview

Rendered in the page, not in an iframe, and it uses CSS container queries instead of media queries. Switching between desktop, tablet and mobile just changes the width of the preview container, and the layout responds as it would on a real device. Before-and-after mode is two previews side by side with two token sets.

### Fonts

Users pick from a curated list of around 16 Google Fonts, loaded with `next/font` and not preloaded, so only the fonts actually in use get downloaded. Free text font names are not accepted, which removes the "invalid font name" failure case and keeps licensing clean.

### State, undo and refresh

One reducer holds the brief, the chosen direction, the current tokens, the website content and the history. Every change (a colour picker, a refinement, a reset) goes through it, which is what makes undo and redo work everywhere. State saves to localStorage with a version number and is validated on load. If a save is missing, stale or corrupt, the app sends the user back to the last stage that is valid rather than showing broken UI.

### Accessibility checks

`lib/accessibility` works out real WCAG contrast ratios for body text, buttons and both themes on every direction. If a pair fails, it shows a warning and suggests the nearest passing colour by adjusting lightness only, so the hue stays on brand. The "identity health" meter is built from these real checks and never shown as a decorative number.

### Refinement engine (Creative Director)

```text
request > classify (strategy / tokens / copy / section / whole site / imagery / motion)
        > structured change object (zod)
        > "I'll update: ..." preview listing affected tokens and sections
        > Apply / Cancel
        > reducer > history (undoable)
```

- The nine preset commands in the spec are deterministic rules, labelled as built in.
- Free text requests go to the server model in live mode and must come back in the same change schema. Changes can only touch token paths and section ids that already exist. Anything else is rejected before it reaches the preview.

### Live mode (server AI)

- `POST /api/directions` (brief in, three directions plus homepage copy out) and `POST /api/refine` (current state plus request in, change object out).
- Separate Anthropic key with its own spend limit, set up the way the personal site's key was.
- Per IP rate limit plus a daily ceiling. These live in memory on each serverless instance, so the only hard ceiling is the console spend limit.
- Default model `claude-sonnet-5` (started on `claude-opus-5`; switched after measuring), overridable with an env var. Usage logged on every call.
- Measured cost per brief: about $0.16 on Sonnet 5, $0.40 on Opus 5. See Phase 10.

## Where the spec needs adjusting

These are the places where following the spec to the letter would work against the concept.

1. **Human photography for the Shared Shore direction.** The brief says to avoid corporate stock photography, and there's no image generation in the stack. Proposal: every direction's imagery is drawn in code (SVG contour lines, grain, duotone shapes coloured by the tokens), which also means imagery changes when tokens change. If Shared Shore still needs photos, a handful of free licence photos with a token driven duotone treatment could be added later. Your call when we reach Phase 4.
2. **Logo directions.** They appear in the product pitch but not in the workflow, and the spec also warns against "generating a random logo and calling it a brand identity". Proposal: a wordmark set in the display typeface plus a simple monogram, both built from tokens. No logo generator.
3. **Uploaded logo or image in the brief.** Superseded by the Materials feature below. Colour reading happens in the browser; sending a file to the model is opt-in per file and arrives with live mode.
4. **Required pages.** The brief collects them, but the MVP builds one homepage, as the spec says. The homepage's navigation links jump to its own sections rather than to pages that don't exist.
5. **PDF export.** Brand guidelines export as HTML with a proper print stylesheet, so "Save as PDF" in the browser gives a clean PDF. No PDF library.
6. **Every export works.** All of them are built from data the project already has, in the browser, so there are no placeholder cards.
7. **Copy.** The spec's sample text includes em dashes, a "not by X, but by Y" line and citation markers ([18][20]) left over from wherever it was drafted. All published copy will be written in your voice, and the final portfolio line reworded before it goes anywhere.

## Materials: building the brand around what people upload

Paul's idea (2026-09-13): let people add things they already have and use them to shape the theme.

**Phase 3 (built):** images only, read entirely in the browser. For each file Loose Brief pulls out the main colours (k-means clustering in OKLab), the exact colours written into SVG files, and plain traits (light or dark, muted or vivid, warm or cool). Each file gets a type (logo, photo, texture, screenshot), a choice between "show it on the site" and "inspiration only", "keep these colours exactly" for logos, and alt text. Files are stored in IndexedDB and never uploaded. The summary shows "colours to keep" and "colours to draw from".

**Phase 10 (built):** Claude reads images and PDFs directly, so no separate image model is needed. Each file is sent only if the visitor ticks it, because it means sending the file to Anthropic. The verdicts below were the plan; everything marked Yes was built.

| Input | What we'd get from it | Verdict |
| --- | --- | --- |
| Images (photos, textures) | Subject, mood, lighting, texture, era, suggested image treatment and illustration style | Yes |
| Logo | Shape language (rounded or angular) for radius tokens, a guess at the wordmark style for type pairing, exact colours (already done) | Yes |
| Screenshots of sites they like | Layout density, type style, colour use. Used for feel, never copied | Yes |
| PDFs: existing brand guidelines, brochures, menus, pitch decks | Existing rules, colours, fonts, tone of voice and copy to reuse | Yes |
| Existing copy (pasted text) | Tone of voice reading, words they use, reading level | Yes, cheap and useful |
| Their current website address | Colours, fonts and copy tone from the live page, fetched on the server | Yes, but needs care: server-side fetching of any URL has to be locked down so it can't be pointed at internal addresses |
| Brand colours they must keep (typed hex values) | Hard constraints for the palette | Yes, trivial |
| Font files they own | Use in the preview only; can't be exported unless their licence allows it | Not built: licensing makes it fiddly |
| Video | A few frames analysed as images | No. Costly, and frames add little over a photo |
| Audio or music | Nothing that maps onto a visual identity | No |
| Social media profile links | Would mean scraping sites whose terms forbid it | No. Screenshots do the same job |

Things to keep in mind: people's photos may show other people, so uploads sent to the model should be deleted straight after analysis; the per-file consent needs to be clear; and every direction should say what it drew from ("navy from your logo, warm light from the harbour photo"), which is also the spec's "show me why".

## Not pursued

Two later phases were planned and then dropped on 2026-09-14, when Paul decided Loose Brief would stay a portfolio piece rather than become a product he promotes and supports:

- **Search and AI visibility**: robots and sitemap files, llms.txt, structured data, social images and a guides section, following Rival Radar.
- **Payments**: a cheap one-off payment per brand to cover the AI cost, which would also have meant accounts, server storage, VAT and terms.

## Definition of done

A visitor can:

1. Open Loose Brief.
2. Load or write a brief.
3. See three clearly different directions.
4. Pick one.
5. Look through the design system behind it.
6. Change a colour or font and watch the website update.
7. Ask the Creative Director for a change.
8. See what will change before it happens.
9. Apply it and undo it.
10. Switch to the mobile preview.
11. Export the tokens or the brand summary.
12. Understand how it's built from the project page.

## Where things ended up

- Repo: public on GitHub. It was private while payments were a possibility, and made public once they were dropped. Keys stay in `.env.local`, which is gitignored; `.env.example` lists what's needed.
- Hosting: a domain so it can be linked from pwilson.dev. Live mode only works where an Anthropic key is set.
- Photos for Shared Shore: decided at Phase 4 to use drawn imagery like the other two directions, since the brief rules out stock photography. Real photos of real places can come later through Materials.
